# Pizza ERP

Ελαφρύ mini-ERP για βιοτεχνία πίτσας: είδη, συνταγές (BOM δύο επιπέδων), αγορές, πωλήσεις (λιανική με backflush και χονδρική), παραγωγές, απογραφές με επιμερισμό διαφορών στο κόστος, καρτέλες πελατών/προμηθευτών. Και online παραγγελίες χωρίς προμήθεια: σελίδα του μαγαζιού για τον πελάτη (με extras και online πληρωμή μέσω Viva ή Stripe), οθόνη κουζίνας με φωνή, και κάθε αποδεκτή παραγγελία γίνεται πώληση με αυτόματη ανάλωση υλικών. Αποδείξεις, τιμολόγια και πιστωτικά μέσω παρόχου ηλεκτρονικής τιμολόγησης (θέση για τον πάροχο, δοκιμαστικός, ή αριθμός από την ταμειακή), και παραγγελίες ξενοδοχείων από δικό τους σύνδεσμο.

- Σχεδιασμός: [docs/DESIGN.md](docs/DESIGN.md)
- Οδηγός «Πες το» για το προσωπικό (όλες οι φράσεις, εκτυπώσιμο A4): [docs/pes-to-odigos.pdf](docs/pes-to-odigos.pdf) (πηγή: `docs/pes-to-odigos.html`)
- Backend: Supabase (Postgres + Auth + RLS). Migrations στο `supabase/migrations/`.
- Frontend: React + Vite + Tailwind, deploy στο Vercel. Η σελίδα του πελάτη είναι στο ίδιο deploy (`/s/<slug>`).

Χρειάζεται PostgreSQL 15+ τοπικά.

  αυτόματο ζυμάρι (πώληση → αυτόματη πίτσα → αυτόματο ζυμάρι, μόνο όσο λείπει
  από το απόθεμα) με ακυρώσεις, κόστη και επιμερισμό απογραφής (και σε δύο
  διαδοχικές απογραφές), απογραφή με ανοιχτές πωλήσεις ημέρας, κλειδωμένες

  μετά και στην επόμενη περίοδο), πρόσθεση από χώρο σε χώρο, απογραφή με το

## Εφαρμογή στη Supabase

- **Νέα εγκατάσταση:** τα migrations `0001`–`0006` με τη σειρά (SQL editor ή
  Supabase CLI / MCP), ή όλα μαζί με το `supabase/apply_all.sql`.
- **Πληρωμές και παραστατικά σε υπάρχουσα εγκατάσταση** (έχει ήδη `0001`–`0005`):
  εφαρμόζεται **μόνο** το `supabase/migrations/0006_pay_fiscal.sql`. Από το
  `0004` αλλάζει μόνο το `_post_sale` (οι υπηρεσίες, π.χ. μεταφορικά, δεν
  κινούν αποθήκη)· από το `0005` ξαναγράφει τις functions των παραγγελιών.
  Ξανατρέχει χωρίς πρόβλημα. Αν ξανατρέξει ποτέ το `0005`, πρέπει να ξανατρέξει
  και το `0006` μετά (αλλιώς γυρίζουν οι παλιές functions των παραγγελιών).
  Πρώτα σε άλλο project ή branch της Supabase και backup. Η εφαρμογή δουλεύει
  και χωρίς το `0006` (οι νέες επιλογές απλώς δεν φαίνονται). Μετά: τα Edge
  Functions (παρακάτω), μόνο αν θέλει online πληρωμή, CAPTCHA ή παραστατικά από
  πάροχο.
- **Online παραγγελίες σε υπάρχουσα εγκατάσταση** (έχει ήδη `0001`–`0004`):
  εφαρμόζεται **μόνο** το `supabase/migrations/0005_online.sql`. Δεν αλλάζει
  καμία υπάρχουσα function· προσθέτει πίνακες, τις functions των παραγγελιών
  και το κανάλι `site`. Ξανατρέχει χωρίς πρόβλημα. Πρώτα δοκιμή σε άλλο project
  ή branch της Supabase και backup, μετά στη βάση που δουλεύει. Η εφαρμογή
  (frontend) δουλεύει και πριν από το `0005`: οι σελίδες των παραγγελιών λένε
  ότι λείπει και τα είδη αποθηκεύονται όπως πριν. Αν ξανατρέξει ποτέ το `0004`
  μετά το `0005`, δεν πειράζει (το `site` είναι και στο `0004`).
- **Υπάρχουσα εγκατάσταση** (έχει ήδη `0001`–`0003`): εφαρμόζεται **μόνο** το
  `supabase/migrations/0004_voice.sql`. Ξανατρέχει χωρίς πρόβλημα αν εφαρμοστεί
  δεύτερη φορά. Οι ήδη καταχωρημένες απογραφές παίρνουν στιγμή μέτρησης λίγο
  πριν από τις δικές τους διορθώσεις (το παλιό κλείδωμα δεν άφηνε κίνηση με
  ημερομηνία ίση ή παλιότερη μετά από αυτές): ό,τι ήταν γραμμένο μένει
  κλειδωμένο όπως πριν, νέες κινήσεις και μετρήσεις της ίδιας μέρας μετράνε
  για μετά. (Το `apply_all.sql` δεν είναι για υπάρχουσα βάση.)

Το `supabase/test/` ΔΕΝ εφαρμόζεται στη Supabase.

### Edge Functions (0006)

Χρειάζονται για online πληρωμή, CAPTCHA και έκδοση παραστατικών από πάροχο
(όχι για μετρητά / κάρτα στην πόρτα ή αριθμό από την ταμειακή). Με το
Supabase CLI, από τη ρίζα του repo:

    supabase functions deploy shop-checkout --no-verify-jwt
    supabase functions deploy pay-return --no-verify-jwt
    supabase functions deploy payments-webhook --no-verify-jwt
    supabase functions deploy pay-refund
    supabase functions deploy fiscal-issue
    supabase secrets set SITE_URL=https://<το-site>

Τα τρία πρώτα τα καλούν ο πελάτης (χωρίς login) και οι πάροχοι πληρωμών,
γι' αυτό `--no-verify-jwt`· ελέγχουν μόνα τους ό,τι χρειάζεται. Τα δύο
τελευταία θέλουν συνδεδεμένο χρήστη της εταιρείας. Το `SUPABASE_URL` και τα
κλειδιά τα δίνει η ίδια η Supabase στο περιβάλλον των functions. Το
`SITE_URL` (π.χ. το domain στο Vercel) είναι η διεύθυνση όπου γυρίζει ο
πελάτης μετά την πληρωμή.

Τα κλειδιά των παρόχων (Viva, Stripe, Turnstile, πάροχος παραστατικών) τα βάζει
ο ιδιοκτήτης στις Ρυθμίσεις site / Ρυθμίσεις παραστατικών. Αποθηκεύονται στο
`integration_secret`, που ο browser δεν διαβάζει ποτέ (μόνο ο server, με
`service_role`).

| Πάροχος | Τι στήνεται |
|---|---|
| Δοκιμαστικός | Τίποτα. Ο πελάτης βλέπει «Πλήρωσε (δοκιμή)» / «Αποτυχία». Για να δοκιμαστεί όλη η ροή |
| Viva.com | Settings → API Access: Smart Checkout client id / secret, Merchant ID, API key. Πηγή πληρωμών με Success και Failure URL `<SITE_URL>/pay/viva`. Webhooks «Transaction Payment Created» και «Transaction Failed» στη διεύθυνση που δείχνουν οι Ρυθμίσεις site. Κάρτα, Apple / Google Pay, IRIS |
| Stripe | Secret key και webhook (checkout.session.completed / async_payment_succeeded / async_payment_failed / expired) με το signing secret |
| Turnstile | Widget στο Cloudflare για το domain· Site Key και Secret Key στις Ρυθμίσεις site |

Παραστατικά: νόμιμη απόδειξη ή τιμολόγιο βγάζει μόνο πιστοποιημένος πάροχος
ηλεκτρονικής τιμολόγησης (ή η ταμειακή / το timologio της ΑΑΔΕ). Ως τότε:
«Από την ταμειακή, με αριθμό» (γράφεται εδώ ο αριθμός) ή «Δοκιμαστικός»
(ψεύτικο ΜΑΡΚ, χωρίς φορολογική αξία). Για τον πάροχο που θα διαλέξει ο
λογιστής: ένα αρχείο `supabase/functions/_shared/fiscal/<όνομα>.ts` που
υλοποιεί το `FiscalProvider` (`types.ts`: η βάση δίνει έτοιμο το παραστατικό με
γραμμές, ΦΠΑ, τύπο myDATA, σειρά και αριθμό), μία γραμμή στο `index.ts`, και
μία στο `FISCAL_PROVIDERS` του `web/src/lib/fiscal.ts`. Τα κλειδιά του
μπαίνουν ως `fiscal_<όνομα>_key` / `fiscal_<όνομα>_user`.

## API προς το frontend

Ο client (supabase-js) γράφει απευθείας σε `item`, `partner`, `bom`, `bom_line`,
`voice_phrase` (δικές τους φράσεις: `phrase` → `meaning`, μία φορά η καθεμία ανά
εταιρεία χωρίς διάκριση πεζών/κεφαλαίων, unique index `voice_phrase_company_phrase`)
και σε πρόχειρα (`draft`) `doc` / `doc_line` (χωρίς `source_doc_id` / `is_auto`:
αυτά τα γράφει μόνο η καταχώρηση). Συνταγές και τιμές πελάτη δέχονται μόνο είδη
και πελάτες της ίδιας εταιρείας. Για όλα τα υπόλοιπα καλεί RPC:

| RPC | Τι κάνει |
|---|---|
| `create_company(p_name, p_vat_no)` | Δημιουργεί εταιρεία, ο χρήστης γίνεται owner |
| `post_document(p_doc)` | Καταχώρηση: κινήσεις αποθήκης / συναλλασσομένων, κοστολόγηση |
| `unpost_document(p_doc)` | Ακύρωση καταχώρησης (αν η περίοδος είναι ανοιχτή και η κίνηση δεν είναι ήδη μέσα σε μέτρηση, βλ. παρακάτω) |
| `explode_bom(p_doc)` | Γεμίζει τις γραμμές ανάλωσης μιας πρόχειρης παραγωγής από τη συνταγή |
| `item_on_hand(p_item, p_until)` | Υπόλοιπο είδους (μέχρι ημερομηνία) |
| `item_price_for(p_item, p_partner)` | Τιμή είδους για πελάτη (ειδική τιμή ή γενική `sale_price`) |
| `tally_add(p_company, p_date, p_channel, p_item, p_delta)` | Μετρητής ημέρας: +/− ποσότητα ετοίμου στην ανοιχτή πώληση της ημέρας για κανάλι λιανικής (`efood`, `wolt`, `box`, `phone`, `store`). Επιστρέφει το id της πώλησης, ή `null` αν άδειασε και διαγράφηκε. Αύξηση σε ημέρα πριν από καταχωρημένη απογραφή (για είδος που θα κινούσε η πώληση, π.χ. αλεύρι μέσω αυτόματου ζυμαριού) απορρίπτεται με «Κλειδωμένη περίοδος…»· η μείωση επιτρέπεται. Την ίδια μέρα με μια μέτρηση περνάει κανονικά (μετράει για μετά τη μέτρηση): αν η μέτρηση καταχώρησε το ανοιχτό πρόχειρο, ανοίγει νέο |
| `stocktake_count(p_company, p_date, p_item, p_qty, p_add)` | Απογραφή σε εξέλιξη της ημέρας: ορίζει τη μέτρηση ενός είδους (με `p_add = true` την προσθέτει, π.χ. «αλεύρι άλλα 5» στον επόμενο χώρο)· `p_qty = null` βγάζει το είδος. Η πρώτη μέτρηση ενός είδους καταχωρεί πρώτα τις πρόχειρες πωλήσεις ημέρας ως σήμερα που το κινούν (ανοιχτές ή απλό πρόχειρο μετά από «Χειροκίνητη επεξεργασία»/ακύρωση· αν κάποια αποτύχει: «Πρώτα πρέπει να καταχωρηθούν οι πωλήσεις ημέρας ΠΩ-…») και κρατά τη στιγμή μέτρησης (`doc_line.stock_cut`)· οι επόμενες προσθέσεις/διορθώσεις κρατούν την ίδια στιγμή. Απορρίπτεται αν υπάρχει καταχωρημένη απογραφή του είδους με μεταγενέστερη ημερομηνία, και (πρώτη μέτρηση σε απογραφή παλιότερης ημερομηνίας, π.χ. ξεχασμένη από χθες) αν το είδος έχει ήδη κινήσεις ή ανοιχτές πωλήσεις ημέρας με μεταγενέστερη ημερομηνία: μετρημένο «τώρα» θα μετρούσαν δύο φορές. Επιστρέφει το id της απογραφής, ή `null` αν άδειασε |
| `close_running(p_company, p_before)` | Καταχωρεί μία-μία τις ανοιχτές πωλήσεις ημέρας με ημερομηνία πριν από `p_before` (οι απογραφές δεν κλείνουν αυτόματα). Επιστρέφει γραμμές `doc_id, doc_no, doc_date, channel, ok, message` |

Ανοιχτά πρόχειρα (`doc.is_running`): ένα ανά εταιρεία / τύπο / ημέρα / κανάλι
(η ανοιχτή απογραφή χωρίς κανάλι). Το "κλείσιμο ημέρας" ή απογραφής είναι απλό
`post_document`. Ακύρωση πωλήσεων ημέρας τις ξανανοίγει (`is_running`), αν δεν
έχει ανοίξει άλλος μετρητής για την ίδια μέρα και κανάλι. Οι πωλήσεις μιας μέρας
και καναλιού μπορεί να είναι σε περισσότερα παραστατικά «Πωλήσεις ημέρας» (όσα
καταχώρησε μια μέτρηση + το ανοιχτό): το σύνολο της μέρας είναι το άθροισμά τους.

Απογραφή "τη στιγμή της μέτρησης": κάθε γραμμή απογραφής κρατά στο
`doc_line.stock_cut` τη θέση του μετρητή των `stock_move.id` τη στιγμή που
μετρήθηκε το είδος (δεν πάει ποτέ πίσω, ούτε όταν ακυρώνεται η τελευταία
κίνηση). Κίνηση είναι "πριν" από τη μέτρηση `(D, cut)` αν
`(move_date, id) <= (D, cut)`. Αναμενόμενο = αυτές οι κινήσεις + οι διορθώσεις
των προηγούμενων μετρήσεων· ό,τι γράφτηκε την ίδια μέρα μετά τη μέτρηση μένει
για μετά (και για την επόμενη περίοδο επιμερισμού). Η αξία της διαφοράς
βγαίνει με το μέσο κόστος τη στιγμή της μέτρησης (αγορά σε άλλη τιμή μετά τη
μέτρηση δεν την αλλάζει). Γραμμές χωρίς στιγμή (απογραφή με το χέρι) παίρνουν
τη στιγμή της καταχώρησης, αφού πρώτα καταχωρηθούν οι πρόχειρες πωλήσεις
ημέρας ως την ημερομηνία της που κινούν τα είδη τους. Για γραμμές με στιγμή
καταχωρούνται μόνο οι πρόχειρες πωλήσεις παλιότερων ημερών (της ίδιας μέρας
είναι μετά τη μέτρηση).

Κλείδωμα: δεν καταχωρείται/ακυρώνεται κίνηση είδους με ημερομηνία πριν από
καταχωρημένη απογραφή του, ούτε ακυρώνεται κίνηση που ήταν ήδη μέσα σε μια
μέτρηση: σε καταχωρημένη απογραφή, ή σε απογραφή σε εξέλιξη / πρόχειρη για
κινήσεις της ίδιας μέρας («Κλειδωμένη περίοδος: το είδος … μετρήθηκε στην
απογραφή [σε εξέλιξη] ΑΠ-… μετά από αυτή την κίνηση…»). Ξανακαταχωρημένη θα
έπαιρνε νέα id και θα μετρούσε για μετά. Για διόρθωση: βγάζεις το είδος από
την απογραφή (`stocktake_count(…, null)` ή με το χέρι· καταχωρημένη: πρώτα
ακύρωση), διορθώνεις, και ξαναμετράς. Ο client μπορεί να διαβάζει/κρατά το
`stock_cut` όταν ξαναγράφει τις γραμμές μιας πρόχειρης απογραφής· τιμή
μεγαλύτερη από τη θέση του μετρητή αγνοείται ("μετρήθηκε τώρα").
Καταχωρήσεις, ακυρώσεις, μετρήσεις και `tally_add` της ίδιας εταιρείας
εκτελούνται μία τη φορά.

Είδος με `make_to_order` (πίτσα, και ημιέτοιμο όπως το ζυμάρι) παράγεται
αυτόματα όποτε πωλείται / αναλώνεται, μόνο όσο λείπει από το διαθέσιμο απόθεμα
της ημέρας: ζυμάρια που φτιάχτηκαν από πριν ή βρέθηκαν στην απογραφή αναλώνονται
πρώτα. Οι αυτόματες παραγωγές ακυρώνονται μαζί με το παραστατικό που τις
δημιούργησε. Στον επιμερισμό απογραφής, ό,τι πέφτει σε αυτόματο ζυμάρι περνάει
ολόκληρο στην πίτσα που το ανάλωσε· ό,τι πέφτει σε χειροκίνητη παραγωγή ζυμαριού
περνάει στις παραγωγές που ανάλωσαν ζυμάρι από απόθεμα από την προηγούμενη
μέτρηση της πρώτης ύλης ως το τέλος της ημέρας της απογραφής (ζυμάρια του
πρωινού αναλώνονται και μετά από μέτρηση στη μέση της μέρας).

Αναφορές: `v_stock_balance`, `v_item_ledger`, `v_partner_balance`, `v_partner_ledger`,
`v_sales_by_partner_item`, `v_purchases_by_partner_item`, `v_production_cost`,
`v_item_cost_monthly`, `v_stocktake_result`, `v_doc_list`, `v_online_month`.

### Online παραγγελίες (0005)

Ο πελάτης ανοίγει τη σελίδα του μαγαζιού (`/s/<slug>`), χωρίς λογαριασμό. Ο
επισκέπτης (`anon`) δεν διαβάζει κανέναν πίνακα: μόνο τρεις functions, με
συγκεκριμένα πεδία (όχι κόστη, τιμές πελατών, προμηθευτές, αποθήκη).

| RPC | Ποιος | Τι κάνει |
|---|---|---|
| `shop_menu(p_slug)` | επισκέπτης | Στοιχεία μαγαζιού (ανοιχτό;, διανομή/παραλαβή, ελάχιστη, μεταφορικά) και τα είδη με `online` (έτοιμα, ενεργά, με τιμή): όνομα, περιγραφή, κατηγορία, τιμή με ΦΠΑ. `null` αν δεν υπάρχει |
| `place_order(p_slug, p_order)` | επισκέπτης | Νέα παραγγελία (`{name, phone, mode, address, payment, notes, lines: [{item_id, qty, note}]}`). Οι τιμές βγαίνουν στη βάση. Έλεγχοι: ανοιχτό μαγαζί, όνομα, τηλέφωνο (ελληνικό 10 ψηφίων ή ξένο με +), διεύθυνση για διανομή, είδη του μαγαζιού στο site, ποσότητες 1–50, ελάχιστη. Όρια: έως 3 ανεπιβεβαίωτες και 6 την ώρα ανά τηλέφωνο, 40 ανεπιβεβαίωτες ανά μαγαζί. Επιστρέφει `{token, order_no}` (αριθμός ανά ημέρα) |
| `order_status(p_token)` | επισκέπτης | Η κατάσταση της παραγγελίας για τη σελίδα του πελάτη |
| `shop_set_open(p_company, p_open)` | μέλος | Ανοίγει (ως την `closes_at`, ώρα Ελλάδας· μετά από αυτήν για δύο ώρες) ή κλείνει το site |
| `order_accept(p_order, p_minutes)` | μέλος | Νέα → δεκτή. Γράφει πώληση με κανάλι `site` (τιμές της παραγγελίας χωρίς ΦΠΑ) και την καταχωρεί αμέσως (backflush, κόστος, κλειδώματα όπως κάθε πώληση). Αν η καταχώρηση αποτύχει (π.χ. πίτσα χωρίς συνταγή), η παραγγελία γίνεται δεκτή και η πώληση μένει πρόχειρη με το μήνυμα στο `stock_note` |
| `order_reject(p_order, p_reason)` | μέλος | Νέα → απορρίφθηκε (καμία κίνηση· ο πελάτης βλέπει τον λόγο) |
| `order_done(p_order)` | μέλος | Δεκτή → έφυγε |
| `order_cancel(p_order, p_reason)` | μέλος | Δεκτή / έφυγε → ακυρώθηκε. Η πώληση ακυρώνεται και σβήνεται· αν την κρατά απογραφή (κλείδωμα ή επιμερισμός), μένει και το λέει |

Ρυθμίσεις: `online_shop` (ένα ανά εταιρεία· βλέπουν τα μέλη, αλλάζει ο owner).
Είδη: `item.online`, `item.description`. Παραγγελίες: `online_order`,
`online_order_line` (μόνο ανάγνωση για τα μέλη· γράφουν οι functions).
Realtime: το `online_order` μπαίνει στο `supabase_realtime`, η οθόνη της
κουζίνας ανανεώνεται και κάθε 20'' για σιγουριά.

Οι online πωλήσεις **δεν** είναι «Πωλήσεις ημέρας» (μετρητής): είναι μία πώληση
ανά παραγγελία, καταχωρημένη τη στιγμή της αποδοχής, γι' αυτό καμία από τις
functions του 0004 (απογραφή, μετρητής, κλειδώματα) δεν χρειάστηκε αλλαγή.
Τα μεταφορικά είναι μόνο στην παραγγελία (`online_order.delivery_fee`), όχι
στην πώληση.

Φωνή: στην οθόνη «Παραγγελίες» και στο «Πες το» (μόνο καθαρές φράσεις, για
να μην μπερδεύονται με πωλήσεις): «δεκτή η 12 σε 20 λεπτά», «απόρριψε την 12
γιατί…», «έφυγε η 12», «έφυγαν όλες», «διάβασε τις παραγγελίες», «κλείσε /
άνοιξε τις παραγγελίες». `web/src/lib/orders/orderVoice.ts`, παραδείγματα στο
`orderExamples.ts` και στον οδηγό (κεφάλαιο 7).

### Πληρωμές, παραστατικά, extras, ξενοδοχεία (0006)

| RPC | Ποιος | Τι κάνει |
|---|---|---|
| `shop_menu`, `place_order`, `order_status` | επισκέπτης | Όπως στο 0005, και: extras (`lines[].extras: [item_id]`, μόνο σε πίτσες κατά παραγγελία), τρόποι πληρωμής του μαγαζιού, κλειδί CAPTCHA. Με CAPTCHA ή online πληρωμή η παραγγελία περνά **μόνο** από τον server (`shop-checkout`) |
| `order_accept` | μέλος | + τα μεταφορικά γίνονται γραμμή της πώλησης (είδος-υπηρεσία «Μεταφορικά», ΦΠΑ 24% αρχικά, αλλάζει στο είδος) |
| `order_reject`, `order_cancel` | μέλος | + `refund: true` αν ήταν πληρωμένη online· η οθόνη καλεί αμέσως το `pay-refund` |
| `order_refund_request(p_order)` | μέλος | Ξανά επιστροφή χρημάτων μετά από αποτυχία |
| `secret_set(p_company, p_name, p_value)` / `secret_names(p_company)` | owner / μέλος | Γράφει (ή σβήνει με κενό) κλειδί παρόχου· ποια έχουν μπει, χωρίς τιμές |
| `fiscal_prepare(p_kind, p_sale_doc, p_order, p_related)` | μέλος | Πρόχειρο παραστατικό από καταχωρημένη πώληση, online παραγγελία ή (πιστωτικό) από εκδομένο. Ένα ανά πώληση, εκτός αν πιστώθηκε. Τιμολόγιο: πελάτης με σωστό ΑΦΜ |
| `fiscal_record_manual(p_id, p_number, p_mark, p_series)` | μέλος | Αριθμός (και ΜΑΡΚ) από την ταμειακή |
| `fiscal_discard(p_id)` | μέλος | Σβήνει πρόχειρο / σφάλμα (με αριθμό μόνο αν είναι ο τελευταίος της σειράς) |
| `fiscal_public(p_token)` | επισκέπτης | Το εκδομένο παραστατικό για τον σύνδεσμο του πελάτη (`/r/<token>`) |
| `partner_order_link(p_partner, p_action)` | μέλος | Σύνδεσμος παραγγελιών πελάτη χονδρικής: `get`, `rotate`, `off` |
| `b2b_menu(p_token)` / `b2b_order_place(p_token, p_order)` | επισκέπτης | Η σελίδα του ξενοδοχείου (`/h/<token>`): είδη με τις τιμές του, παραγγελία → πρόχειρη πώληση χονδρικής για έλεγχο |
| `b2b_seen(p_id)` | μέλος | «Το είδα» στην οθόνη Παραγγελίες |

Μόνο για τον server (`service_role`): `service_secrets`, `shop_checkout_info`,
`shop_pay_settings`, `payment_context`, `payment_start`, `payment_abort`,
`payment_confirm` (έλεγχος ποσού, ξανά ίδιο event = τίποτα, πληρωμή σε
ακυρωμένη / ληγμένη = επιστροφή), `payment_failed`, `payment_lookup`,
`refunds_due`, `payment_refunded`, `fiscal_check`, `fiscal_begin` (αριθμός τη
στιγμή της έκδοσης, χωρίς κενά), `fiscal_done`.

Η πληρωμή online: η παραγγελία μένει `awaiting_payment` (δεν τη βλέπει η
κουζίνα) ως την επιβεβαίωση από τον πάροχο (επιστροφή του πελάτη ή webhook,
όποιο έρθει πρώτο· ποτέ από τον browser). Όσες μείνουν απλήρωτες πάνω από 3
ώρες γίνονται `expired` (με την επόμενη παραγγελία του μαγαζιού).

Πίνακες: `online_payment`, `fiscal_settings`, `fiscal_doc`, `fiscal_counter`,
`b2b_order` (ανάγνωση για τα μέλη), `integration_secret` (κανένας από τον
browser). Νέα πεδία: `item.is_extra`, `item.is_service`, `partner.tax_office`,
`partner.postal_code`, `partner.country`, `partner.order_token`,
`online_shop.pay_*`, `online_shop.captcha_site_key`, `online_order.pay_status`,
`online_order_line.parent_line`.

Φωνή: «απόδειξη για την 12» (οθόνη Παραγγελίες και «Πες το»).
